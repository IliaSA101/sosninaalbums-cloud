# Журнал развилок 0.1

Решения оркестратора без вопроса владельцу: вопрос → варианты → выбор → почему. Владелец просматривает
журнал перед выпуском версии; несогласие — переделка в следующей версии.

## 29.10.2026 — проверка только под Linux

Вопрос: нужна ли пара `check.sh` + `check.ps1`, как в настольных проектах.
Варианты: а) обе; б) только `scripts/check.sh`.
Выбор: б. Почему: сервис собирается и работает только в Linux-контейнере; второй сценарий проверки
расходился бы с первым без пользы.

## 29.10.2026 — линтер без исключений путей и прав

Вопрос: оставлять ли привычные исключения `gosec` G301/G302/G304/G306 (права каталогов и файлов,
путь из переменной).
Варианты: а) оставить, как в настольных проектах; б) убрать.
Выбор: б. Почему: сервис пишет на диск файлы, пришедшие из сети, по путям из запроса — это ровно те
места, где ошибка становится уязвимостью. Ложное срабатывание закрывается точечно с причиной.

## 29.10.2026 — модуль контракта подключается позже

Вопрос: подключать ли модуль контракта `/v1` (`api/albums` настольной программы) в `go.mod` сейчас.
Варианты: а) `replace` на локальный путь сейчас; б) когда модуль появится.
Выбор: б. Почему: модуль ещё не создан, `replace` на несуществующий путь ломает сборку. Для публичной
сборки нужна выпущенная версия модуля (метка `api/albums/v0.1.0`) — это решение владельца программы.

## 31.10.2026 — продуктовые вводные к спеке MVP (решения владельца)

Вопросы владельцу с вариантами; он выбрал рекомендованный вариант во всех четырёх.

1. Кто пользуется сервисом в 0.1. Варианты: а) один фотограф с заделом; б) только один фотограф, без задела;
   в) сразу несколько, с токенами и квотами. Выбор: а. Один токен загрузки, но на диске каталог на каждого
   фотографа: второй фотограф добавляется строкой в конфиге, без переноса данных и смены ссылок.
2. Скачивание разворотов клиентом. Варианты: а) только листать; б) кнопка «скачать всё» (архив);
   в) решить позже. Выбор: а. Кнопки нет. Архив можно добавить позже без переделки хранилища.
3. Альбом после срока ссылки. Варианты: а) удалить сразу; б) скрыть на 30 дней; в) хранить до удаления
   фотографом. Выбор: а. Файлы удаляются с диска, из бэкапа уходят по ротации (152-ФЗ: не хранить дольше
   нужного). Совпадает с контрактом 146: «Срок истёк — альбом удалён с сервера» → «Выгрузить заново».
4. Что видит клиент. Варианты: а) альбом и имя студии; б) только альбом; в) бренд и контакты.
   Выбор: а. Название альбома из манифеста и подпись студии фотографа.

## 31.10.2026 — откуда берётся имя студии

Вопрос: передавать имя студии в манифесте или держать на сервисе.
Варианты: а) новое поле контракта `/v1`; б) настройка фотографа в конфиге сервиса (inventory).
Выбор: б. Почему: контракт не меняется (он у программы); имя одно на фотографа, а не на альбом; домен

## 31.10.2026 — спека 001 (сервис MVP)

Решения по рекомендуемому варианту после ревью, аудита безопасности и второго мнения; подробности —
`001-albums-svc/design.md`. Необратимое (1, 4, 5, 14, 15, 20) — второе мнение до кода. Отступления от
решения по стеку (1, 2, 4, 5, 8, 20) — владельцу на просмотр.

- **001-1. Раскладка `data/`.** Варианты: а) плоско `albums/<id>` + `meta/<id>.json`, Caddy читает
  `albums/`; б) каталог на владельца, корень Caddy по заголовку; в) `LAYOUT` (версия 1, `flock`),
  `owners/<slug>/albums/<id>/{meta.json,<sha256>.jpg}`, `tmp/`, `trash/`, `quarantine/` на одном разделе,
  Caddy к данным доступа не имеет. Выбор: в. Почему: каталог на фотографа (решение владельца) без групп и
  ACL для Caddy в rootless; `meta` рядом со страницами — удаление одним `rename` в `trash/`; версия
  раскладки и `flock` — защита от второго экземпляра и от старого кода на новой раскладке.
- **001-2. Кто отдаёт `/a/<id>/…`.** Варианты: а) Caddy `file_server` после `forward_auth` на каждый
  запрос; б) сервис сам (`http.ServeContent`), Caddy — TLS и `reverse_proxy`. Выбор: б (решение
  оркестратора). Почему: а) упирается в порядок директив Caddy (корень из заголовка клиента, стирание
  скопированного заголовка, переписанный URI) и права rootless-тома для Caddy; б) — один источник правды о
  доступе, единый 404, ~50 строк Go; прототип проходит `Conformance` за секунду. Заодно и `/viewer/*`
  отдаёт сервис (листалка встроена через `embed`, имена с хэшем), а не статика Caddy: один образ — одна
  версия листалки и HTML альбома.
- **001-3. Имена страниц.** Варианты: а) по номеру; б) по `sha256` внутри альбома; в) общим хранилищем
  владельца. Выбор: б. Почему: неизменённые страницы не грузятся заново, удаление — один каталог, страницы
  разных клиентов не пересекаются.
- **001-4. Cookie входа.** Варианты: а) `__Host-sa_session`, `Path=/`; б) `__Host-sa<tag>`, `Path=/`
  (второе мнение); в) `__Secure-sa_session`, `Path=/a/<id>/`, `Secure`, `HttpOnly`, `SameSite=Lax`.
  Выбор: в, значение `1.<epoch>.<exp>.<mac>`; сервер строит строку заново и сравнивает целиком; все
  одноимённые cookie через `CookiesNamed`, не больше 4. Почему: при а) вход во второй альбом затирает
  первый, при б) браузер шлёт все входы на каждый запрос; `__Host-` несовместим с путём альбома;
  нестрогий разбор base64 пропускал подделки (прототип). `Lax`: ссылка из мессенджера иначе каждый раз
  просит пароль.
- **001-5. Пароль и секрет.** Варианты: а) HMAC с перцем из переменной окружения, соль — id; б) HMAC от
  `salt ‖ id ‖ NFC(TrimSpace(p))`, соль 16 Б на альбом и новая при смене пароля, ключи `pw/1`, `cookie/1`,
  `log/1` через HKDF из одного файла секрета (base64url ≥ 32 Б, секрет Podman, `mode=0400`). Выбор: б.
  Почему: новая соль закрывает прежние входы при смене пароля (строже контракта — К7); обрезка и NFC —
  «ё» и пробел с телефона не делают пароль другим; файл не попадает в отладочные выводы окружения; в `meta`
  метки `alg`/`key` — задел на смену ключа без ротации в MVP.
- **001-6. WebP.** Варианты: а) `x/image/webp`; б) свой разбор заголовка; в) выключить в 0.1 конфигом
  `accept_webp: false`. Выбор: в. Почему: программа шлёт только JPEG, `Conformance` успешный WebP не
  проверяет, а свой разбор — лишняя поверхность. Включение потом — с требованиями: заголовок ≤ 64 байт,
  проверка переполнения смещений, размер RIFF = длина − 8, VP8X совпадает с кадром, анимация — 400,
  `FuzzWebPHeader`, отказ от чанков EXIF/XMP.
- **001-7. Лимит попыток.** Варианты: а) по IP; б) IP и альбом+IP; в) три ключа с суточным окном по
  альбому, проверка и учёт атомарно до сверки пароля. Выбор: в. Почему: пароль «Придумать» ≈ 21 бит держит
  только предел по альбому; без атомарности параллельные попытки проходят сверх предела.
- **001-8. Метрики Prometheus.** Варианты: а) в MVP; б) к этапу 7. Выбор: б. Почему: хранилища метрик нет,
  лишний эндпоинт — лишняя поверхность; здоровье — `GET /v1/health`.
- **001-9. Формат конфига.** Варианты: JSON (stdlib), YAML/TOML (зависимость), переменные окружения.
  Выбор: JSON. Почему: без зависимостей; список владельцев и токенов в переменных неудобен.
- **001-10. Токен в конфиге.** Варианты: открытым, `sha256`, HMAC с секретом. Выбор: `sha256`. Почему:
  32 случайных байта по хэшу не перебрать; утечка конфига не даёт токен.
- **001-11. Квота.** Варианты: а) без квоты; б) `quota_bytes`, `max_albums`, запас места — на `POST`/`PUT`
  альбома и на `PUT` страницы до чтения тела; замена правки удаляет файлы прежней правки. Выбор: б.
  Почему: украденный токен иначе забивает диск сервера, в том числе бесконечной заменой правки; ответ —
  `413` (К2).
- **001-12. `max_days`.** Варианты: 365 (по умолчанию модуля) или 366. Выбор: 366. Почему: «Год» в
  високосный год.
- **001-13. Файлы прежней редакции.** Варианты: удалить при `publish` или держать час. Выбор: удалить те,
  которых нет в новой `published`. Почему: отдаются только файлы опубликованного манифеста — запас доступа
  не дал бы; листалка на 404 картинки перечитывает манифест.
- **001-14. `meta.json`.** Варианты: а) плоская схема без версии; б) `format: 1`, `published`/`draft`,
  `password {alg,key,salt,hash}`, `epoch`; неизвестные поля сохраняются; формат новее — отказ старта;
  id/owner не сходятся с путём — карантин. Выбор: б. Почему: откат образа не должен ни терять поля, ни
  удалять альбомы (прототип показал потерю полей).
- **001-15. Формат id.** Варианты: а) 22 знака base64url (128 бит); б) 26 знаков base32 строчными
  (130 бит). Выбор: б. Почему: `_`, `-` и регистр ломаются разметкой и автозаменой мессенджеров; формат
  проходит `CheckID` контракта.
- **001-16. Связь Caddy с сервисом.** Варианты: а) TCP на loopback; б) unix-сокет, контейнер
  `Network=none`. Выбор: б, запасной — а) с `trusted_proxy`. Почему: в rootless-сети источник соединения не
  обязательно loopback; сокет закрывает соседей по машине и подделку `X-Sa-Client-IP`.
- **001-17. Вход без IP клиента.** Варианты: общий ключ или `503`. Выбор: `503` и строка журнала. Почему:
  общий ключ даёт любому закрыть вход всем 20 неудачами.
- **001-18. id в журнале.** Варианты: первые знаки id или 8 hex `HMAC(k_log, id)`. Выбор: HMAC. Почему:
  префикс — часть ключа доступа, HMAC сопоставим между строками и ничего не раскрывает.
- **001-19. Скачок часов.** Варианты: доверять часам или сторож. Выбор: сторож — при скачке вперёд или
  назад (старт: `last_seen` старше 30 дней или в будущем; работа: расхождение с монотонными > 10 мин)
  пауза всех удалений по времени, записанная в `LAYOUT` и переживающая перезапуск; снимает разовый
  `albums-svc -clock-ok` по runbook, не флаг юнита. Почему: неверные часы иначе удалят все альбомы
  разом; пауза только в памяти снималась бы первым же `auto-update`; доступ всё равно решается по
  времени запроса. (Уточнено по повторному ревью.)
- **001-20. Бэкап.** Варианты: а) только `meta` и конфиг, страницы дозагрузит программа; б) `data/`
  целиком, шифрованно, ≤ 30 дней, без секрета; после восстановления `epoch++` у всех. Выбор: б. Почему: в
  программе дозагрузка есть только у изменённого альбома; снимок мог быть до сброса входов. Альбом,
  удалённый между снимком и сбоем, вернётся до уборки по сроку — принятый риск.
- **001-21. Принято без мер.** `RemoveAll` не затирает блоки диска; картинки с `immutable` остаются в кэше
  браузера клиента и после отзыва.
- **001-22. Домен ссылок.** Варианты: выдавать ссылки с временного поддомена или только с конечного.
  Выбор: только с конечного. Почему: ссылка живёт до 366 дней — временный поддомен пришлось бы держать с
  переадресацией весь этот срок.
- **001-23. Уборка мусора в работе.** Варианты: а) одна уборка всего мусора при старте и каждые 5 минут;
  б) при старте — всё, в работе — только `tmp/` старше 600 с, `trash/` и каталоги без `meta`, которых нет
  в индексе, под мьютексом альбома. Выбор: б. Почему: а) режет идущий `PUT` (до 540 с) и чужой
  `writeAtomic`, удаляет каталог между `MkdirAll` и записью `meta` в `POST`. Неразбираемый `meta.json` — в
  `quarantine/`, не удаление.
- **001-24. Отдача файла при `ENOENT`.** Варианты: а) любой `ENOENT` помечает альбом неполным; б) fd
  открывается под `RLock` альбома после проверки имени в текущей `published`, неполным помечает только
  `ENOENT` файла текущей редакции. Выбор: б. Почему: а) после `publish` клиент со старым манифестом
  запросит удалённый файл прежней редакции и выключит весь альбом до перепубликации.
- **001-25. Маркеры JPEG.** Варианты: а) чёрный список (APP1); б) белый: APP0, APP2, APP14, COM, DQT, DHT,
  SOFn, DRI. Выбор: б. Почему: IPTC (APP13) и прочие APPn тоже несут метаданные. COM разрешён: программа
  пишет в каждую страницу свою метку, образцы `Conformance` тоже (факт: код и ответ программы).
- **001-26. id вне грамматики на `/v1`.** Выбор: после токена — `404 not_found` тем же телом, что у
  несуществующего. Почему: так ждёт `Conformance` (`"Zz"+24×q` → 404, `a×22` без токена → 401).

## 31.10.2026 — замок второго экземпляра (001-27, по коду Г1)

- **Вопрос.** design §2 ставил `flock` на `data/LAYOUT`, но `LAYOUT` переписывается атомарно (`rename`):
  новый inode без замка — второй экземпляр взял бы его и стартовал.
- **Варианты.** а) отдельный пустой `data/LOCK` только под замок; б) переписывать `LAYOUT` на месте
  (теряется атомарность записи); в) замок на каталоге `data/` (`flock` на каталоге работает не везде).
- **Выбор: а.** Ревью подтвердило, тест `TestStoreLock` берёт замок и делает `SetLayout`. Раскладка
  `data/` необратима — `LOCK` добавлен в неё сейчас, до первой выгрузки. `verify` открывает хранилище
  только на чтение (`OpenReadOnly`), без замка.

## 31.10.2026 — развёртывание: решения по пачке И1

- **Откуда Caddy.** В Debian 13 пакет Caddy 2.6.x — без поля `client_ip` в журнале и части директив,
  на которых держится маска журнала. Варианты: а) пакет Debian; б) официальный apt-репозиторий Caddy
  (stable) с нижней границей версии; в) бинарник релиза с GitHub по sha256. **Выбор: б** — обновления
  безопасности приходят штатно (unattended-upgrades), а версия в роли проверяется не ниже той, на которой
  прошла `caddy validate` в проверках `deploy/tests/`. `admin off` — роль только перезапускает Caddy, не `reload`.
- **Предел памяти.** `Memory=` в Quadlet Podman 4.9 нет — `PodmanArgs=--memory=…` (переносимо на 5.x).
- **CLI сервиса — договорённость для Г2.** Запуск `albums-svc -config <файл>`; проверка живости —
  подкоманда `albums-svc health -config <файл>` со своим `FlagSet` (`flag` останавливается на первом
  позиционном аргументе); сокет — `chmod 0660` сразу после `Listen`. Доступ Caddy к сокету — см. ниже
  «по аудиту И1» (keep-id заменён на subuid + ACL).
- **Сборка листалки.** Шага сборки нет: каталог `/viewer/<версия>/`, версия — хэш встроенных файлов,
  считает сам сервис при старте (В1). Containerfile копирует `web/` как есть, сборка из чистого клона
  повторяется. Контекст сборки — белым списком (`.containerignore`).

## 31.10.2026 — развёртывание: решения по аудиту И1

- **Маска журнала Caddy.** Три `regexp` на одно поле `request>uri` в Caddy 2.6.2 (пакет Debian/Ubuntu)
  дают только последний фильтр — id альбомов уходят в журнал, `caddy validate` молчит (проверено аудитом).
  Варианты: а) только свежий Caddy; б) один `regexp`, оставляющий первый сегмент пути. **Выбор: оба** —
  Caddy из официального репозитория (выше) и один фильтр, не зависящий от версии; он же закрывает обходы
  вида `//a/<id>/`, `/A/<id>/`, `/%61/<id>/`, которые Caddy пропускает в сервис. Проверка журнала —
  на той версии, что будет на сервере.
- **Доступ Caddy к сокету.** `UserNS=keep-id` делает процесс контейнера uid `albums` на хосте: выход из
  контейнера даёт хозяина `~albums` (Quadlet, образы, секреты Podman, свой контейнер с сетью). Варианты:
  а) keep-id + группа (принять риск); б) обычная карта subuid + ACL на каталоге сокета (default `u:caddy:rw`,
  на каталог `u:caddy:x`), проверено аудитом на стенде. **Выбор: б** — после выхода из контейнера атакующий
  чужой uid без прав `albums`; Caddy не в группе `albums` и не читает `config.json`.
- **Конфиг при subuid.** Процесс контейнера — чужой uid на хосте, каталог `/etc/albums-svc` (0750
  root:albums) ему закрыт (повторный аудит). **Выбор:** ACL на uid процесса (`subuid_base+65531`: каталог
  `rx`, файл `r`), владелец и режимы прежние, Caddy и прочие без доступа; роль ставит ACL после каждой
  записи `config.json`. Фильтр журнала сужен до первого сегмента из ≤ 8 букв и цифр — в самодельных путях
  вида `/<id>/x` остаются 8 из 26 знаков id (40 из 130 бит), подобрать ссылку по ним нельзя.
- **Запись в контейнере.** Podman с `--read-only` монтирует `/run` и `/var/tmp` на запись и с правом
  запуска. **Выбор:** `ReadOnlyTmpfs=false`, тома `/data` и сокета — `noexec,nosuid,nodev`.
- **Мелкое.** `request_buffers 4KiB` на вход и `/a/*`; `protocols h1 h2` (тайм-ауты тела на QUIC не
  действуют); пределы в KiB/MiB; образ — только с дайджестом (проверка в шаблоне); секрет file-драйвера
  лежит на диске открытым — `~albums/.local/share/containers` исключить из бэкапа (этап 4); в группе
  `albums` нет людей и пользователя развёртывания — требование к роли.

## 31.10.2026 — листалка: решения по пачке В1 (001-28)

- **Имена с хэшем.** Варианты: а) `app.<hash8>.js` у каждого файла, ставит шаг сборки (как в design);
  б) каталог `/viewer/<версия>/`, версия — хэш всех встроенных файлов, считает сервис при старте.
  **Выбор: б** — без шага сборки и переписывания относительных импортов, `immutable` честный, сборка
  из чистого клона повторяется. Цена — при любой правке листалки у клиента перекачиваются все её файлы
  (десятки КБ), приемлемо.
- **404 без стилей.** Caddy отдаёт `notfound.html` сам, в том числе при 502, и хэша каталога не знает;
  одинаковые байты держат единый 404 сервиса и Caddy. Страница — на стилях браузера.
- **Стили StPageFlip.** Библиотека вставляет `<style>` при загрузке, CSP без `unsafe-inline` его режет:
  строка стилей вынесена в `vendor/page-flip-2.0.7.css` дословно, `.js` библиотеки не правится, версия
  закреплена суммой (`TestVendorPinned`). В П1 — проверка, что событий `securitypolicyviolation` ноль.

## 31.10.2026 — сервис: решения по пачке Г2

- **Запас места при правке без новых байт.** Варианты: а) проверять запас на любой записи; б) проверять
  только при новых байтах. **Выбор: б** — переименование или смена срока не занимают места, а при нехватке
  места фотограф должен иметь возможность править и удалять. То же для повторного PUT уже лежащей
  страницы: файл на месте — запас не проверяется, ответ 204 (идемпотентность под давлением диска).
- **Один sha256 с разными описаниями.** Страницы с одинаковым sha256, но разными `type`, `bytes`, `w`, `h`
  в одном manifest → 400 `bad_manifest`: файл на диске один, описания противоречат друг другу; у честного
  клиента одинаковые байты дают одинаковое описание.
- **Неверный метод на известном пути.** Варианты: а) 405 `method_not_allowed` с `Allow`; б) 404
  `not_found`. **Выбор: б** — в enum кодов контракта /v1 нет `method_not_allowed`, программа такого кода не
  знает; 404 не раскрывает ничего лишнего. Расширение контракта не нужно.
- **Ссылка на альбом в выводе `verify`.** id — ключ доступа, в выводе и журналах runbook его быть не
  должно. **Выбор:** первые 8 hex sha256 от id (32 бита из 130) — по нему альбом находится в `data/`
  через тот же `verify`, а id не восстановить.
- **Память на JSON-запросах (аудит Г2).** Тело до 1 МиБ разбиралось в `[]Page` целиком (≈ 200 МБ на
  `{"pages":[{},{},…]}`) до сверки с пределом — 2–4 параллельных запроса роняют процесс по OOM при
  `--memory=256m`. Варианты: а) семафор на JSON-запросы; б) потоковый разбор `pages` с отказом после
  `limits.Pages+1`; в) оба. **Выбор: в** — (б) ограничивает память одного запроса пределом страниц,
  (а) — число одновременных (общий 2, на владельца 1; занято → 429 `rate_limited` с `Retry-After`, код есть
  в контракте).
- **Запас места проверяется, но не резервируется.** Параллельные PUT страниц одного владельца могут выйти
  за запас не больше чем на слоты × `page_bytes` (≈ 120 МБ при запасе 2 ГБ). Принято: резервирование
  усложняет откат на обрыве, а перерасход ограничен слотами.
- **Возраст «идущей» записи для уборки.** `.part` моложе `ActiveAge` не трогается; `ActiveAge` считается
  не меньше наибольшего срока чтения тела страницы плюс запас, чтобы медленный, но живой клиент не терял
  файл. **Остаток сокета.** Перед удалением — пробное подключение: ответил — работает другой экземпляр,
  старт с ошибкой (два экземпляра с разными `data/` и одним `listen`).

## 31.10.2026 — сервис: решения по пачке Г3 (вход в листалку)

- **Решения исполнителя приняты.** Проверка по контракту гоняется на боевой сборке в `cmd/` (depguard
  запрещает `api`→`view`); GET формы входа → 303 на `/a/<id>/` (обновление страницы после неверного пароля
  не ломается); POST у альбома без пароля → 303 без cookie; 413 формы попыткой не считается (пароль не
  читался); имя страницы — `names.ValidPageName` (`jpg|webp`, как в листалке; webp при выключенном приёме
  в published не попадает → 404); неканонический `/v1` → HTML-404, как у самого Caddy; токена CSRF у формы
  нет — без пароля вход не подделать (001-7), плюс SameSite=Lax и `form-action 'self'`. В design §4
  регулярка пути показывает только `\.jpg` — верным считать `jpg|webp` из кода.
- **Срок записи картинки.** Caddy в `reverse_proxy` ответ не буферизует, поэтому при WriteTimeout 120 с
  разворот 15 МиБ обрывался у клиента медленнее ~1 Мбит/с. **Выбор:** перед отдачей картинки продлевать
  срок записи до `min(540 с, 30 с + размер / 32 КиБ/с)` — тот же расчёт и потолок, что у PUT (меньше
  `write` у Caddy).
- **Блокировка входа через ключ «альбом» (аудит Г3).** Держатель ссылки 20 неверными паролями в сутки
  закрывал вход всем без cookie, и фотограф ничего не мог сделать. Варианты: а) принять и записать;
  б) ключ альбома по id + соли пароля + epoch — смена пароля или «сбросить входы» дают новую корзину;
  в) убрать ключ альбома. **Выбор: б** — у фотографа появляется рычаг, а предел перебора на альбом
  (20 в сутки на пароль) остаётся. Остаток принят: пока нападающий продолжает, новый пароль снова
  блокируется через сутки попыток; клиенты с cookie не страдают.
- **Атомарность доступа и файла.** Проверка входа и открытие манифеста или файла идут по одному снимку
  альбома (под мьютексом), чтобы пароль, поставленный между вызовами, не пропускал ответ.
- **Принято без правок.** Подброс cookie с соседнего поддомена (`Domain=` и длинный `Path` закрывают
  листалку одному клиенту; `__Host-` невозможен из-за Path) — учитывать при выборе домена: родительский
  домен без чужих поддоменов. Подделка `X-Sa-Client-IP` локальным процессом в TCP-варианте — как 001-16.
  CSP на `/viewer/` ставит Caddy — содержимое встроено при сборке. Порядок `handle @login` раньше
  `handle /a/*` в Caddyfile (предел 4 КиБ формы) проверить на стенде П1; если не так — явный `route`.

## 31.10.2026 — стенд П1: где матрица и чем гонять

- **Матрица доступа.** Спека кладёт её в `tests/access/` на pytest + httpx, но на машине нет ни pytest, ни
  httpx, а ставить в систему без согласия владельца нельзя; у исполнителя проверок нет права записи.
  Варианты: а) просить владельца поставить пакеты и расширить права; б) матрица в `deploy/tests/access/`
  (стенд и так в `deploy/tests/`), pytest + httpx — внутри контейнера Python с дайджестом, зависимости по
  `requirements.txt` с `--require-hashes`, на хосте ничего не ставится. **Выбор: б** — состав проверок и
  оси design §10 те же, меняется только место и способ запуска.
- **Листалка в браузере.** Playwright не ставим — листалку проверяют во встроенном браузере (телефон
  390×844, ПК 1440×900) по критериям спеки. Стенд для браузера открывается по http на localhost: Chromium
  считает localhost безопасным контекстом и принимает cookie `Secure`, а сертификат `tls internal` дал бы
  предупреждение. Матрица при этом идёт по https, как в бою.

## 31.10.2026 — стенд П1: решения по ревью и аудиту

- **Заголовки безопасности в Caddy 2.11.7.** Все «?»-поля одного блока `header` собираются в одно условие
  «ни одного из полей нет в ответе»; сервис всегда ставит `X-Content-Type-Options`, поэтому CSP на
  `/viewer/` и заголовки на `/v1` не ставились. **Выбор:** одно «?»-поле — одна директива; `-Server`,
  `-Via` и HSTS — отложенные (HSTS не задвоится, если сервис его пришлёт). Срез `X-Sa-*`/`X-Forwarded-*`
  перед каждым `reverse_proxy` проверяется по `caddy adapt` в `caddy-validate.sh`: тест подмены его не
  ловит, потому что `header_up` и так затирает адрес.
- **Единый 404 от Caddy.** У 404, 413 и 502 Caddy убираются `Via`, `Vary` и заголовки Range и условных
  запросов до `file_server` — иначе его 404 отличался от 404 сервиса по байтам.
- **Стенд.** Рабочий каталог — только в `XDG_RUNTIME_DIR` (0700), иначе отказ; тестовые контейнеры без
  лишних прав, в контейнер Conformance идёт только отслеживаемое (без приватных каталогов и `.git`).
  Токены через `--env-file` видны в `podman inspect` живого контейнера — принято: стенд локальный,
  токены одноразовые.

## 31.10.2026 — спека 002 (подъём сервера)

Развилки спеки [002-provisioning.md](002-provisioning.md) после ревью и аудита безопасности; доводы и
проверки — в [research.md](002-provisioning/research.md).

- **002-1. Токен API провайдера.** Варианты: `TF_VAR` в окружении и `plan -out`; `podman run -e`; файл в
  tmpfs; дескриптор. **Выбор:** переменная `sensitive` + `ephemeral`; токен из файла секретов (002-2)
  кладётся файлом 0600 в `XDG_RUNTIME_DIR` учётной записи раскатки и монтируется только на чтение; обёртка в
  контейнере читает его и делает `exec tofu`; файл удаляет `provision.sh` на хосте по выходу; интерактивный
  `apply` без файла плана. Почему: файл плана хранит значение открытым текстом, значение из `-e` видно в
  `podman inspect` и на диске, `export` уносит токен в историю оболочки. Остаток — процессы той же учётной
  записи раскатки во время прогона.
- **002-2. Граница доступа.** Варианты: меры внутри учётной записи владельца и страж; отдельная учётная запись
  с входом через `sudo -iu`; отдельная учётная запись с отдельной сессией на текстовой консоли. **Выбор
  (решение владельца 31.10, уточнено):**
  - *учётная запись и вход:* отдельная учётная запись раскатки со своим паролем; вход только на текстовой
    консоли (VT); `sudo -iu`/`su` из сессии владельца runbook запрещает. `provision.sh` отказывает под чужой
    учётной записью, при признаке сессии помощника, при `DISPLAY`/`WAYLAND_DISPLAY`, если сессия не
    `Type=tty` своего uid, если `XDG_RUNTIME_DIR` не `/run/user/<uid>`, чужой или не 0700;
  - *секреты:* один файл, зашифрованный age по фразе (scrypt), 0600 в доме раскатки: токен, пароль vault,
    фразы ключей сервера и забора, ключ age копий. Расшифровывает контейнер-контроллер по фразе с консоли при
    каждом запуске, без кэша; дальше — каналы (`--preserve-fds`, отдельный на каждый плей), токен — файл 0600
    в `XDG_RUNTIME_DIR`. Ключи SSH — ed25519 с фразой в собственном `ssh-agent` на время прогона. Вывод
    расшифровки — каналом `age -d -o /dev/fd/3`, терминал только для фразы; каждый контейнер `sa-prov-*` — с
    `--log-driver=none`; учётная запись раскатки не в `adm` и `systemd-journal`;
  - *источник кода:* `git bundle` из каталога входящих или `file://`, в клоне fsck объектов, отказ при
    `alternates`; дом владельца раскатке не открывается; bundle открывается по `realpath` внутри каталога
    входящих, симлинк — отказ; каталог входящих создаёт root на консоли (0755, владелец), вне любого git-дерева;
  - *просмотр:* до «yes» — полный `git diff --text --no-color --no-ext-diff --no-textconv` от последнего
    развёртывания по `deploy/`, странице 404 и `.gitattributes` в `less` без `R` и с `LESSSECURE=1`; отказ,
    если изменился любой `.gitattributes` или в `deploy/` есть управляющие символы, кроме `\t` и `\n`; хэш
    пишется после успешной раскатки. Контроллер собирается раскаткой и запускается по ID.
  Страж — защита от случайности, не граница. Почему: процессы помощника того же uid читают секреты и меняют
  код раскатки; в графической сессии владельца ввод перехватывается и подделывается (XTEST, XInput), под
  `sudo -iu` сессия, `XDG_RUNTIME_DIR` и устройства — владельца; askpass на консоли не работает, а с дисплеем
  подтверждается подделанным нажатием; diffstat не показывает содержания; клон по пути переносит
  `alternates`; вывод контейнера conmon по умолчанию пишет в journald, а журнал раскатки читает владелец
  через `adm`. Остаток вне границы: подмена `~/.bashrc`/`PATH` владельца крадёт его пароль `sudo` в его
  терминалах — совет runbook. Подписанный тег и FIDO2 — позже.
- **002-3. IP.** Варианты: адрес в блоке `addresses` сервера; отдельная привязка. **Выбор:**
  `clo_network_ip_attach`. Почему: удаление сервера провайдер выполняет вместе с его адресами.
- **002-4. Защита SSH.** Варианты: счётчики в nftables; средства sshd. **Выбор:** `PerSourcePenalties` и
  `MaxStartups`. Почему: динамический набор nft без срока заполняется сканерами и закрывает SSH всем.
- **002-5. nftables.** Своя таблица `inet`, drop на всех интерфейсах, открыты 22/80/443; применение только
  `reload` (остановка юнита делает `flush ruleset`); второй рубеж — проверка слушающих портов.
- **002-6. subuid.** Диапазон `albums` — из inventory в 100000–524287, ни с чем не пересекается; у
  администратора и пользователя бэкапа subuid нет. Почему: пересечение даёт администратору без sudo uid
  процесса сервиса.
- **002-7. Где полный прогон.** Локально — без задач запуска сервиса (rootless-цели не хватает uid), полный
  прогон и повторный — в CI на rootful-цели. Расширять subuid на машине разработки — правка системы, нет.
  Стенд запускается с `--cap-add NET_ADMIN,SYS_ADMIN,DAC_READ_SEARCH`, иначе юниты с песочницей падают
  с 226/NAMESPACE; `PrivateNetwork` проверяется только на аренде.
  Локальный стенд (`run.sh`, цель, шаг `static`) — отдельная первая задача
  П2a; `verify_backup_stream` и `verify_restore_rejects` — в CI (им нужен `data/` от задач запуска сервиса).
  Отказ tar в тесте — drop-in стенда `SystemCallFilter=~getdents64` + `SystemCallErrorNumber=EIO`.
- **002-8. Версия Caddy.** Варианты: не ниже 2.11.7 с обновлениями из unattended; ровно 2.11.7. **Выбор:**
  ровно. Почему: поведение заголовков менялось между версиями (стенд П1). Уточняет запись «Откуда Caddy»
  (И1): исправления безопасности приходят не сами — до этапа 7 еженедельная сверка с GHSA, на этапе 7 —
  Renovate с проверкой Caddyfile и стендом.
- **002-9. Агент провайдера в ВМ.** Варианты: выключить; `--block-rpcs`; белый список. **Выбор:**
  `--allow-rpcs` (ping, sync, info, fsfreeze, shutdown). Почему: снимки с заморозкой ФС нужны, сброс пароля
  нет; новые команды агента закрыты по умолчанию. Риск «кабинет или токен = диск через rescue» принят.
- **002-10. Бэкап на старте.** Состав по 001-20; поток через сокет к службе с `CAP_DAC_READ_SEARCH`, которая
  видит только данные, конфиг и программы (`TemporaryFileSystem=/:ro` + `BindReadOnlyPaths`); ключ забора
  с `restrict,command=`; шифрование к ключу владельца. Метка `SA-END` — вторым архивом только при коде tar
  ≤ 1, проверяется последним членом через `--ignore-zeros`; нет метки — копия отвергается. Пути из tar в
  журнал не попадают. Копии — у учётной записи раскатки, расшифровка только в поток. ACL не подходит: маска
  у файлов 0600. Почему: неполную копию иначе не отличить от целой, обрыв `age` — гонка.
- **002-11. Секреты и state.** ansible-vault (встроен, без лишнего инструмента; пароль ≥ 128 бит, хранится в
  файле секретов 002-2); state — без шифрования в приватном репозитории: секретов в нём нет по построению,
  это проверяется.
- **002-12. Пользователь образа.** Переменная `image_user`, проверка, что он не совпадает с администратором;
  в `bootstrap` — блокировка, снятие ключей и файла sudoers, в `site.yml` — `loginctl terminate-user` и
  `userdel`; root закрывается только после проверенного входа и sudo администратора. Повторно `bootstrap` не
  запускается: есть вход администратора — только `site.yml`. Стенд входит через пользователя образа с файлом
  sudoers как от cloud-init. Почему: `userdel` текущего пользователя или пользователя с живыми процессами
  падает, а при повторе с входом администратора его можно принять за пользователя образа.
- **002-13. cloud-init.** Варианты: оставить; выключить сразу; убрать модули пользователей, паролей и ключей.
  **Выбор:** убрать модули — полной копией списков модулей образа без трёх (списки в `cloud.cfg.d` заменяются
  целиком); полное выключение — переменная, решение по пробной аренде. Код через `bootcmd`/`runcmd` из
  кабинета — принят, как rescue. Почему: неизвестно, зависит ли сеть образа провайдера от cloud-init.
- **002-14. Возврат копии.** Варианты: поток в `sudo` по ssh; `NOPASSWD` на скрипт возврата; файл на сервере
  и `become` с паролем. **Выбор:** третий — файл в каталоге администратора, `become` с паролем из vault; root
  только создаёт временный каталог (uid сервиса, `umask 077`) и отдаёт поток; разбор архива и распаковка
  (zstd, tar) — от uid сервиса через `setpriv`: только обычные файлы и каталоги, без `..`, абсолютных путей и
  ссылок, `--no-same-owner`, предел размера распакованного и проверка свободного места. Скрипт возврата и
  проверка отказов — в И4, запуск в CI. Почему: в потоке stdin занят архивом; `NOPASSWD` расширяет ущерб от
  кражи ключа; разбор и распаковка от root недоверенного архива (age не удостоверяет отправителя) дают ему
  права root при ошибке в zstd или tar.
- **002-15. Срок копий.** Варианты: строго ≤ 30 дней; ≤ 30 дней, кроме самой новой проверенной. **Выбор:**
  строго ≤ 30 дней (как решил владелец в 001-20) — таймер учётной записи раскатки по дате в имени; от потери
  всех копий защищает проверка свежести: самая новая старше 7 дней — предупреждение при каждом запуске
  `provision.sh` и в выводе таймера. Почему: хранить фото клиентов дольше срока, в том числе удалённые по
  сроку альбомы, — отступление от решения владельца; остановку забора видно за три недели до потери.
- **002-16. Команды `provision.sh`.** `up`, `apply [--replace-server]`, `configure`, `backup`, `forget-host`;
  `plan` нет (интерактивный `apply` показывает план, «no» отменяет). `--replace-server` подставляет
  фиксированный `-replace` сервера. Почему: иначе для пересоздания сервера tofu вызывали бы руками.
- **002-17. Откуда сервер берёт образ сервиса (решение владельца 31.10).** Варианты: публичный GHCR из CI;
  сборка учётной записью раскатки и `podman save | ssh podman load`; решить позже. **Выбор:** GHCR — образ
  собирает CI по метке выпуска (выпуск — с «да» владельца) с аттестацией сборки, дайджест — в приватном
  inventory. Почему: код и так открыт, секретов и домена в образе нет; серверу не нужны ключи реестра; Quadlet
  остаётся с проверкой дайджеста, на этом же строится обновление этапа 7. Владелец также дал «да» на шаги

## 31.10.2026 — роли сервиса, Caddy и бэкапа И4: решения по ревью и аудиту

Ревью: 2 блокера и 7 важных; аудит: 3 «важно», 5 «низко», блокеров нет. Пересекаются поток бэкапа и
`policy-rc.d`. Все правки — одной пачкой исполнителю, затем повторные ревью и аудит.

- **И4-1. stderr службы забора — в журнал.** `StandardOutput=socket` без `StandardError` дублирует stderr в
  сокет: строка `sa-backup: tar code=…` и сообщения zstd/age встают внутрь потока, ни одна копия не
  расшифруется. **Выбор:** `StandardError=journal`; `verify_backup` сверяет через `systemctl show`
  `StandardError`, `SystemCallFilter`, `BindReadOnlyPaths`, `ProtectHome` (довод «`CAP_DAC_READ_SEARCH` видит
  только данные» держится на них). Плюс бесплатное ужесточение юнита: `RestrictNamespaces=yes`,
  `SystemCallArchitectures=native`, `LockPersonality=yes`, `ProtectKernel*`.
- **И4-2. Каталог Caddy для сертификатов.** Пользователь `caddy` создаётся без дома — ACME негде хранить
  состояние, TLS на аренде не поднимется, стенд (TCP 443) этого не видит. **Выбор:** явная задача
  `/var/lib/caddy` caddy:caddy 0700, дом пользователя в passwd — он же; проверка в `verify_caddy`.
- **И4-3. Строгий разбор листинга в `sa-restore`.** Огромный `mtime` в pax-заголовке печатается одним числом,
  первое слово имени уходит в «дату» — правила `charset`/`prefix`/`marker` обходятся (только внутри `new/`).
  **Выбор:** `NF == 6`, дата `^[0-9]{4}-[0-9]{2}-[0-9]{2}$`, время `^[0-9]{2}:[0-9]{2}$`; мутации на `charset`,
  `sum`, `space` и на подложенный член с `mtime=1e17`. Сумма — каждый член как `4096 + size`, округлённый до
  4096, и предел числа членов: пустые каталоги весят 0, а занимают inode и блоки. Восьмеричные константы —
  явно. Работник — только uid из диапазона subuid `albums` (защита в глубину).
- **И4-4. `policy-rc.d` не остаётся навсегда.** `always` не выполняется при обрыве SSH; следующий прогон
  счёл бы файл чужим и молча прошёл, а `exit 101` блокирует перезапуски служб и после обновлений
  безопасности. **Выбор:** файл с меткой `# sa-caddy-install`, снимается по совпадению содержимого; чужой —
  `fail` (не молчаливый пропуск); `verify_caddy` проверяет, что `/usr/sbin/policy-rc.d` нет. Смена
  `caddy_version` при запрете перезапуска — `register` + перезапуск, если служба активна.
- **И4-5. Caddyfile — до пакета, как в design §8.** Иначе после обрыва между пакетом и Caddyfile Caddy после
  перезагрузки отдаёт пакетную витрину. **Выбор:** Caddyfile кладётся до установки (`force-confold`),
  `caddy validate` — отдельной задачей до запуска. design не меняется.
- **И4-6. Ключ apt — ровно один armor-блок.** После первого `END` — только пробельные символы, ровно один
  `BEGIN`, сверка CRC24; мутация «второй блок».
- **И4-7. Сузить права Caddy.** Это единственный процесс, разбирающий интернет. **Выбор:** в drop-in
  `CapabilityBoundingSet=` и `AmbientCapabilities=` — только `CAP_NET_BIND_SERVICE` (`CAP_NET_ADMIN` нужен
  Caddy лишь для буферов UDP HTTP/3 — их дать через `sysctl` `net.core.rmem_max`/`wmem_max`), `NoNewPrivileges`,
  `ProtectHome`, `ProtectKernel*`, `RestrictNamespaces`, `SystemCallFilter=@system-service`,
  `SystemCallArchitectures=native`; `ExecStart` без `--environ` (окружение не в журнал). Действующие значения —
  в `verify_caddy` через `systemctl show`.
- **И4-8. Мелкие ошибки ролей и стенда.** `albums_svc` verify сравнивает `stat.uid`, а не `pw_name` (у uid
  из subuid нет записи в passwd); `--tags albums-runtime` отдельно работает (задачи-факты, нужные ему, —
  с этим тегом); `apt update`, если у `caddy` нет кандидата; свой `*_name_re` вместо переменной чужой роли;
  у стенда `vault.yml` с `vault_albums_master`; disable SC2034/SC1091 после `shellcheck -x` — убрать, где
  не нужны, оставшиеся — точечно с причиной; длинная строка `run.sh`; шапка `target.Containerfile` — верный
  набор способностей.
- **И4-9. Развилки исполнителя — принять** (в design §1, §5, §8, §12 впишет аналитик): `SYS_PTRACE` — только
  у цели стенда; дом и `authorized_keys` `sa-backup` — у root; белый список имён в `sa-restore`; стенд —
  `--skip-tags albums-runtime`, полный прогон — `SA_STAND_FULL=1` в CI; юниты — шаблоны `.j2`;
  `grep -q` → `grep -c` (усиление).
- **И4-10. Непроверенное на стенде.** `verify_backup_stream` (забор → `age -d` → `tar -t` → `SA-END`) —
  главная дыра: И4-1 стенд не поймал. **Выбор:** на стенде — локальный шаг потока от root по тестовому
  ключу age; если в rootless-цели невыполним (PrivateNetwork, сокет) — в П2 первым пунктом, с причиной.
  `/v1/health` через сокет от `caddy`, `verify_after_restart`, `idempotence_full` — явно в П2.
- **И4-11. `conf/` из копии не ставится в `/etc/albums-svc`.** age не удостоверяет отправителя: подложенный
  `conf/config.json` с чужим sha256 дал бы токен загрузки. **Выбор:** конфиг — только из inventory;

  design §12 к этапу 7.
- **И4-12. Место на диске при возврате — принять.** Сжатая копия пишется на раздел `data/` до проверки

  systemd-networkd. Локально (rootless) `ds-identify` cloud-init выключает, networkd не стартует, адрес
  Podman остаётся. Варианты: запретить cloud-init сеть; замаскировать networkd; оба; DHCP-сервер в сети
  стенда; статический адрес. **Выбор:** оба. Почему: адрес цели даёт рантайм, как адрес ВМ — провайдер;
  роли и проверки networkd не используют; DHCP — лишняя движущаяся часть стенда, статика расходится с
  боевой выдачей адреса; маска — от прочих источников сетевых конфигов. Правка только в образе цели стенда.
  Причина — гипотеза (H3; почему в CI `ds-identify` включает cloud-init — предположительно DMI виртуалки
  виден в rootful), подтвердит прогон. Гипотеза прогона 3 (в `prepare`
  `net.bridge.bridge-nf-call-iptables=0` против FORWARD DROP Docker) не помогла, но и не вредит — оставлена.
- **П2-8. Вложенный crun в CI.** Прогон 4: сеть есть (П2-7), раскатка дошла до `albums-svc` — ACL, chown
  данных, секрет, образ по дайджесту, старт юнита прошли, но контейнер не создаётся: conmon «Failed to create
  container: exit status 255», текста crun в выводе нет. subuid `200000:65536` в `userns=auto:size=300000`
  помещается — эта причина снята. Варианты: только диагностика; диагностика + `seccomp=unconfined` у цели;
  править Quadlet (убрать лимиты памяти и pids). **Выбор:** второе. Почему: профиль seccomp на одноразовой
  цели стенда ничего не защищает (AppArmor и маска уже сняты), вложенный crun часто упирается именно в него;
  правка Quadlet меняла бы боевой артефакт ради стенда. `albums_diag.sh` (только чтение: журнал пользователя
  сервиса, Quadlet-юнит, карты id, cgroup, ручные запуски с `--log-level=debug`; секрет создаётся с `no_log`
  через stdin и в журнал не попадает) выводится при провале `converge_site` и в `ci.sh diag`; если причина
  иная — флаг вернуть. Причина — гипотеза до прогона.
- **П2-9. Проверка здоровья через shell.** Прогон 5: `albums_diag` показал, что контейнер сервиса стартует
  («сервис запущен»), но каждый `podman healthcheck run` падает: conmon «runtime stderr: executable file
  `/bin/sh` not found» → «Failed to create container: exit status 255». Причина: `HealthCmd=` в Quadlet-шаблоне
  задан строкой, Podman выполняет строку как `/bin/sh -c …`, а в distroless-образе оболочки нет. После трёх
  неудач `HealthOnFailure=kill` убивает контейнер, юнит перезапускается по кругу. Это дефект боевого шаблона,
  а не стенда. Локальный стенд не использует Quadlet и снимает `HealthCmd`, поэтому раньше не ловилось.
  Варианты: exec-форма (JSON-массив) в `HealthCmd`; убрать проверку здоровья; добавить оболочку в образ.
  **Выбор:** exec-форма. Почему: проверка остаётся (перезапуск зависшего сервиса), образ остаётся без оболочки.
  В `podman inspect` теперь `CMD`, а не `CMD-SHELL` — проверено локально; `quadlet-validate.sh` проверяет
  exec-форму в выводе `quadlet -dryrun`. Гипотеза П2-8 опровергнута: «exit status 255» в прогоне 4 давал тот же
  exec проверки. `seccomp=unconfined` у цели убран, `albums_diag.sh` оставлен.
- **П2-10. Нестабильный тест подделки cookie.** Прогон 5: `TestViewPasswordAccess` изредка видел 200 на
  «подделке». Подделка строилась заменой последнего знака подписи на «A». У base64url от 32 байт в последнем
  знаке значимы лишь 4 бита, поэтому примерно в 1/16 случаев «подделка» совпадала с настоящей cookie. Сервис
  исправен: проверка сравнивает всю строку за постоянное время. Варианты: менять знак в середине подписи на
  гарантированно другой; перебирать все знаки (как `TestCookieTamper`). **Выбор:** первое (`tamper` в тестах
  `internal/view`). Почему: тест проверяет маршруты, а не формат cookie; порча задевает значимые биты подписи и
  всегда даёт другое значение. Остальные порчи в тестах (`internal/access`, `internal/config`) детерминированы —
  проверено.


## 03.11.2026 — раскатка: отдельная ВМ раскатки вместо учётной записи в рабочей ВМ (решение владельца)

Поправка к спеке [002-provisioning.md](002-provisioning.md): техрешение — [design §16](002-provisioning/design.md),
отвергнутое — [research §4](002-provisioning/research.md). Правка кода и стража — по задачам design §16.9.
Устройство хоста — см. приватные заметки.

- **ВР-1. Где граница раскатки.** Варианты: (а) `sa-ops` в рабочей ВМ по runbook (recovery-режим GRUB, вход
  только на текстовой консоли, `pam_access`) — как в design §2; (б) облегчённый `sa-ops` в рабочей ВМ (вход
  через `sudo -iu` или графическую сессию, без recovery); (в) отдельная ВМ раскатки (ops-ВМ): полный клон чистого
  снимка Ubuntu 24.04, без агентов, Claude и Node, администратор владельца с `sudo` и `sa-ops` без `sudo`;
  (г) раскатка из CI (секреты в GitHub); (д) всё под учётной записью владельца в рабочей ВМ. **Выбор (владелец,
  03.11):** (в). Почему: вариант (а) на деле неудобен и хрупок — через удалённый доступ к хосту Esc в ВМ не
  доходит, при `GRUB_TIMEOUT=0` меню GRUB не открыть, то есть recovery недоступен; каждый вход раскатки требовал
  выхода из графического сеанса. (б) не граница: агент под учётной записью владельца подменяет `sudo` и
  перехватывает ввод (design §2, research §3). (г) переносит токен провайдера и ключи в чужую систему, против
  приватного решения по аккаунту провайдера (см. приватные заметки). (д) отдаёт секреты агентам. Граница (в) —
  ВМ: агент в рабочей ВМ может что угодно под владельцем (и root через подменённый `sudo`), но в ops-ВМ его
  процессов нет. Цена — память хоста под вторую ВМ и её обслуживание.
- **ВР-2. Что защищает код в ops-ВМ.** Код раскатки приходит из рабочей ВМ, где агент пишет что угодно,
  поэтому против агента рубеж ровно один — владелец читает полный diff в `review.sh` до checkout (И2-1). Остальные
  проверки (fsck, белый список символов, режимы, второй взгляд, метка машины) помогают читать и ловят ошибки, но
  не заменяют чтения. Записано явно, чтобы не создавать впечатления второй границы.
- **ВР-3. Канал доставки bundle в ops-ВМ.** Варианты: общая папка VMware (одна папка хоста: в рабочей ВМ на
  запись, в ops-ВМ только на чтение — гостевым `ro` и флагом папки на стороне хоста); сеть между ВМ (HTTP или
  `git daemon` в рабочей ВМ, ops-ВМ забирает); перекладка владельцем на хосте из папки рабочей ВМ в папку ops-ВМ;
  GitHub как посредник; съёмный диск или ISO. **Выбор:** общая папка VMware, точка монтирования в обеих ВМ —
  `/srv/sa-inbox` (значение по умолчанию `SA_INBOX` не меняется). Почему: ops-ВМ ничего не слушает и сама не
  ходит к рабочей ВМ; обратного пути из ops-ВМ нет; `vmhgfs-fuse` и open-vm-tools в рабочей ВМ уже есть
  (проверено 03.11). Сеть требует слушателя и адреса рабочей ВМ (меняется по DHCP) и даёт парсер HTTP против
  сервера агента; перекладка на хосте — лишний ручной шаг без проверки (в файловом менеджере bundle не прочесть);
  GitHub — публикация непросмотренного `dev` и внешняя зависимость; диск и ISO — неудобно без выигрыша. Остаток:
  папка — добавочная поверхность рабочей ВМ к HGFS хоста и путь заполнить диск хоста; принято (design §16.2).
- **ВР-4. Чтение bundle из общей папки.** Агент меняет файл в любой момент. **Выбор:** копия в дом через
  `dd iflag=nofollow,count_bytes count=<предел+1>` вместо `head -c` (симлинк, подложенный между проверкой
  `-L` и открытием, даёт ELOOP — проверено прототипом 03.11 на coreutils рабочей ВМ), дальше — как сейчас:
  предел 200 МиБ, verify и `fsck --strict` во временном репозитории. Монтирование в ops-ВМ —
  `ro,nosuid,nodev,noexec,umask=022`; стоп в runbook — только если `findmnt` не показывает `ro` (гостевой `ro`
  действует независимо от хоста). Запись в рабочей ВМ — во временное имя и `mv` (атомарность переименования на
  HGFS — гипотеза). Тест гонки не пишется: `ctl_shared` статически проверяет `dd … iflag=nofollow,count_bytes` в
  `review.sh` и README, простой симлинк ловит `[ -L ]`.
- **ВР-5. Защита от запуска `provision.sh` не в той машине.** Сессия на текстовой консоли и отказ при
  `DISPLAY`/`WAYLAND_DISPLAY` теряют смысл: в ops-ВМ графика разрешена. Варианты: признаки рабочей ВМ
  (процессы `claude`/`node`, каталоги агентов) — перечень запретов, по умолчанию «разрешено»; файл-метка
  машины раскатки от root — по умолчанию «запрещено»; оба. **Выбор:** метка обязательна —
  `/etc/sa-ops-machine`, root, без записи группе и прочим, содержимое побайтово `sa-ops-machine <machine-id>\n`,
  где `/etc/machine-id` — ровно 32 hex (иначе отказ); клон ops-ВМ после смены machine-id метку теряет — нужен
  явный шаг администратора. Плюс дешёвый отказ при живом процессе `claude` или `node` любого пользователя; `ps`
  не выполнился — отказ. Путь метки в коде постоянный (без переменной окружения): тесты подставляют файлы
  монтированием. Проверка — и в `provision.sh`, и в `review.sh`. Это защита от ошибки владельца (секреты в
  рабочей ВМ), не от агента.
- **ВР-6. Проверка сессии в ops-ВМ.** **Выбор:** снять требование `Type=tty` и отказ при `DISPLAY`/`WAYLAND_DISPLAY`;
  оставить `XDG_SESSION_ID`, `Type` ∈ {`tty`, `x11`, `wayland`}, `User` = свой uid, `Remote=no`, `XDG_RUNTIME_DIR`
  = `/run/user/<uid>`, свой, 0700. Почему: файл токена и сокет агента живут в `XDG_RUNTIME_DIR`, rootless Podman
  без него уходит в `/tmp`. Что `sudo -iu`/`su` из сессии администратора дают отказ — гипотеза, её проверяет
  владелец в ops-ВМ (И5f); смысл отказа теперь — правильное окружение, а не перехват ввода. Вход `sa-ops` —
  обычным входом в GDM.
- **ВР-7. `INCOMING` в страже Claude Code.** Граница теперь — ВМ, страж остаётся защитой от случайности.
  **Выбор:** `INCOMING = ['/srv/sa-inbox', '/mnt/hgfs']` (точка монтирования папки в рабочей ВМ и стандартная
  точка VMware): агенты не читают и не пишут каталог входящих, bundle кладёт владелец своей командой. Почему:
  папка — единственный путь агентов на диск хоста и к тому, что читает ops-ВМ; случайная перезапись bundle во
  время цикла просмотра путает владельца. Правка оснастки — только оркестратор с «да» владельца.
- **ВР-8. Подлинность того, что ставится в ops-ВМ из сети.** **Выбор:** пакеты — только из архива Ubuntu
  (apt проверяет подпись `InRelease`), без PPA и сторонних репозиториев; образы — по дайджесту (как сейчас);
  провайдер tofu — lock-файл и первая сверка (README §4); pip — с хэшами в контроллере. Отдельной сверки ISO
  нет: ВМ — клон снимка, доверие к нему — со слов владельца («снимок до агентов»). Новых сверок не нужно.
- **ВР-9. Симлинк на месте метки.** Варианты: отказ при `-L`; не проверять. **Выбор (оркестратор по ревью):** не
  проверять — `guard_machine` смотрит то, что читается (`stat -L`, содержимое). Почему: в `/etc` пишет только
  root, цель ссылки проходит те же проверки владельца, режима и содержимого, то есть реального пути отказ не
  закрывает; тест дорогой — `-v` в Podman разрешает симлинк источника, нужен отдельный образ.
- **ВР-10. Копия bundle: отклонения от буквы §16.4 (по ревью и аудиту И5).** Вопрос: хватает ли
  `dd … iflag=nofollow,count_bytes` и копии в доме. Выбор: `timeout 120 dd … iflag=nofollow,nonblock,count_bytes,fullblock`;
  временный каталог создаётся до копии и скрытый (`~/.review.XXXXXX`, umask 077), копия и временный репозиторий — внутри,
  уборка в trap; ручной первый просмотр в README — так же. Почему: без `fullblock` GNU dd при коротких чтениях (возможно
  у FUSE общей папки) считает блоки по числу read, а не байты, и молча режет копию (проверено на coreutils 9.4);
  `nonblock` — FIFO, подложенный после `[ -f ]`, даёт пустую копию (verify откажет), а не вечное ожидание открытия;
  `timeout` — страховка; скрытый каталог — индексатор файлов графической сессии разбирает видимые файлы в доме, а
  копия — чужие данные. Сообщение при сбое: «копия bundle не удалась или обрезана». `ctl_shared` проверяет строку.
- **ВР-11. Шире шаблон процессов и защита от индексатора.** Выбор: `guard_machine` (и копия в `review.sh`, побайтово)
  отказывает при `claude`, `claude-*` (например `claude-desktop`), `node`, `cowork*`; код `grep` > 1 — тоже отказ.
  В runbook §1: `mask` двух юнитов индексатора GNOME в сессии `sa-ops`, `x-gvfs-hide` в `fstab` общей папки, правило
  «папку bundle открывать только через `review.sh`, не файловым менеджером»; проверки «нет слушающих служб» (`ss -tulpn`,
  `dpkg -s openssh-server`). Почему: метка и процессы — защита от ошибки, а не граница, но перечень имён рабочей ВМ
  шире двух слов; у `sa-ops` теперь графическая сессия, и файловые службы GNOME читают то, что туда попало.
- **ВР-12. Предел памяти вокруг verify, fetch, fsck — не вводится.** Варианты: `ulimit -v`/cgroup вокруг git; не
  вводить. Выбор: не вводить. Почему: худший исход — отказ в обслуживании раскатки (процесс убьёт ОС или зависнет
  ops-ВМ), секреты и код он не затрагивает; bundle собирает владелец, предел размера файла (200 МиБ) и `timeout` у
  копии уже есть, а лимит git — лишняя настройка, ломающая законные большие деревья.
- **ВР-13. `guard_session` без `XDG_SESSION_ID` (находка И5f, ops-ВМ, 04.11).** Факт: в GNOME Terminal
  `XDG_SESSION_ID` не задан (gnome-terminal-server — потомок `systemd --user`), и ВР-6 в первой редакции отказывал
  всегда. Варианты: (а) требовать `export XDG_SESSION_ID=…` руками; (б) при пустом брать `Display` из
  `loginctl show-user <uid>`; (в) убрать проверку сессии. **Выбор:** (б). Пусто и там — отказ «нет сессии: ни
  XDG_SESSION_ID, ни графической сессии учётной записи»; дальше те же проверки по найденной сессии (Type, User, Remote)
  и без изменений проверки `XDG_RUNTIME_DIR` (они отсекают `sudo -iu`/`su -`). Добавлено `State` ∈ {active, online} для
  обоих путей: `closing` и прочее — отказ (runtime-каталог вот-вот исчезнет), `online` пускаем — сессия без фокуса
  после переключения консоли то же окружение; цена — одно поле в том же вызове. Почему не (в): цель проверки (ВР-6) —
  окружение для токена, сокета агента и Podman, а не граница; дешёвая мера остаётся. Тесты: shim `loginctl` отдаёт
  `show-user`, `FAKE_DISPLAY`, `FAKE_STATE`; сверяется, по какой сессии спрашивали. README §1: проверка под `sa-ops` в
  форме, работающей в обоих случаях; `users` (100) в `id sa-ops` — норма Ubuntu 24.04, опасны `sudo`, `adm`, `lxd`.
- **ВР-14. Исходящая сеть ops-ВМ вместо построчного чтения первого просмотра (решение владельца 04.11).** Вопрос:
  первый diff — ≈ 13,6 тыс. строк, владелец построчно его не читает; чем ограничить вред испорченного кода. Варианты:
  (а) читать всё (ВР-2 как есть); (б) режимы по политике `ufw` для исходящих — «подготовка» (`allow`, без ввода
  фраз) и «раскатка» (`reject`, разрешены только точные адреса API провайдера tcp 443, сервера tcp 22 и сервера
  DHCP сети NAT udp 67; DNS закрыт, имя API — в `/etc/hosts`); (в) то же по uid `sa-ops`, без режимов для всей ВМ;
  (г) диапазоны АС провайдера вместо точных адресов; (д) прокси с белым списком имён; (е) DNS к шлюзу NAT
  оставить открытым. **Выбор:** (б), переход в раскатку — с перезагрузкой; раскатка — обычное состояние, окно
  подготовки — только при смене образов, зависимостей контроллера или провайдера и для обновлений (не реже раза в
  месяц); секреты в ops-ВМ появляются только после первого перехода в раскатку; новая команда `provision.sh
  prepare` (без секретов), `tofu init` в `apply` — без сети с `-plugin-dir` (design §16.10). Почему: (б) — одна
  команда переключения и пять-семь постоянных правил, которые владелец читает глазами. (в) не держит DNS: имена
  разрешает системный резолвер (другой uid, D-Bus, varlink), туннель через DNS уносит токен одной строкой. (г) —
  сотни префиксов общего хостинга: приёмником станет любая дешёвая аренда у того же провайдера. (д) — белый список
  включает GitHub и реестры, а через них выгрузка на чужой аккаунт. (е) — тот же туннель. Перезагрузка: `ufw`
  пропускает уже установленные соединения. Остаток (design §16.10): выгрузка через свой сервер или аккаунт
  провайдера и отложенная выгрузка в окне подготовки — против целевой атаки рубеж прежний, чтение diff; мера
  снимает общий случай (`curl`/DNS на любой адрес). Деньги токена ограничены балансом (см. приватные заметки).
- **ВР-15. Провайдер tofu — архивом выпуска с GitHub, без реестра OpenTofu (решение владельца 04.11, по факту из ops-ВМ).**
  Вопрос: из России `registry.opentofu.org` отвечает 403 (Cloudflare, `loc=RU`), поэтому `tofu providers lock` (README §4) и
  `tofu init` в `prepare` не работают; GitHub и `ghcr.io` доступны, хэши `zh:` lock-файла с `SHA256SUMS` релиза совпали. Варианты:
  (а) VPN для ops-ВМ; (б) открыть в окне ещё и зеркало реестра или прокси; (в) брать архив провайдера с GitHub и ставить
  локальным зеркалом (filesystem mirror, packed layout), `init -plugin-dir` без сети; (г) положить архив в репозиторий.
  **Выбор:** (в). Почему: (а) отвергнут — лишняя сторона и сложнее сеть; (б) расширяет круг адресов в окне, ради которого и
  строилась ВР-14; (г) двоичный файл ≈ 7 МБ в публичном репозитории и обход сверки lock. (в) использует то, что и так открыто в
  окне Б (GitHub), и оставляет init и validate без сети. Детали (design §16.10.1): версия, источник и платформа — только из lock;
  `prepare` (`ops/mirror.sh`) скачивает архив и `SHA256SUMS` `curl`-ом хоста (https, TLS 1.2, таймаут, предел размера), сверяет
  sha256 архива со строкой `SHA256SUMS` и с `zh:` в lock — оба обязательны, расхождение — отказ до зеркала; зеркало —
  `inventory/tofu/.terraform-clo/mirror` (вне git); `init` из него в `--network=none`, затем `validate` — он, а не init, сверяет `h1`
  (проверено на образе tofu 1.13.5: init пропускает неверный `h1` при верном `zh:`); `apply` берёт тот же каталог без сети и сам
  сверяет `h1`. README §4 — сверка без реестра (`providers lock -fs-mirror`, `--network=none`). Остаток: подпись `SHA256SUMS`
  не проверяется, доверие — GitHub и сверка lock владельцем один раз. Попутно (И5h-1): после `cron.allow`
  `crontab -l -u sa-ops` отказывает, проверка — `sudo ls -A /var/spool/cron/crontabs/` (пусто). Сверка lock выполнена
  владельцем 05.11.2026, совпало (sha256 архива = `SHA256SUMS` = `zh:`, `h1` linux_amd64 совпал, код 0).
- **ВР-16. База контроллера — с `mirror.gcr.io`, а не с `public.ecr.aws` (находка в ops-ВМ 05.11.2026).**
  Вопрос: сеть ops-ВМ выходит из РФ, и `podman pull public.ecr.aws/docker/library/python@sha256:2d44…` зависает: каждый
  слой встаёт на ~16 КиБ (слои ECR отдают CloudFront/S3 — известное ограничение к части зарубежных хостингов); API
  `public.ecr.aws/v2/` при этом отвечает 401 быстро, `ghcr.io` и GitHub работают. `mirror.gcr.io/library/python@sha256:2d44…`
  скачался целиком (код 0, ID образа bdfc738a8a869292…). Варианты: (а) `FROM mirror.gcr.io/library/python@<тот же дайджест>`;
  (б) `registries.conf` с зеркалом в ops-ВМ; (в) перенос образа через канал bundle; (г) `dockerhub.timeweb.cloud/library`.
  **Выбор:** (а). Почему: дайджест индекса тот же, содержимое проверяется по нему, поэтому доверие к зеркалу не нужно;
  (б) отвергнут — невидимая настройка вне репозитория, тесты и CI шли бы другим путём; (в) — шире канал и сложнее;
  (г) — российский провайдер с тем же дайджестом, но зеркало Google официальное и проще; остаётся запасным вариантом, если
  `mirror.gcr.io` станет недоступен (меняется одна строка FROM). Остальные образы ops-ВМ (tofu) — с `ghcr.io`, не затронуты.
  Контроллер в стенде и CI тоже идёт с `mirror.gcr.io` (общий Containerfile, `lib.sh` `ensure_lint_image`); не менялись образы
  цели стенда, реестра, Caddy и Go (`public.ecr.aws`, `docker.io`) — в ops-ВМ они не выполняются. `mirror.gcr.io` — кэш
  популярных образов, старый дайджест может быть вытеснен: это даст отказ, но не подмену; при плановом обновлении базы брать
  свежий дайджест, запасной вариант — (г).
- **ВР-17. Буфер обмена ops-ВМ выключен; токен CLO — одной загрузкой с буфером до появления секретов (решение владельца 06–07.11.2026).**
  Вопрос: при выключенном буфере токен CLO (длинный, выпускается в панели console.clo.ru на машине владельца) и длинные
  команды §3 пришлось бы набирать руками — неудобно и источник опечаток. Опасное направление — из ops-ВМ наружу: фразы
  ssh/файла секретов и пароль администратора, который §3 печатает один раз, при копировании внутри ВМ ушли бы в буфер
  хоста, оттуда через RustDesk на машину владельца и в рабочую ВМ к агентам. Варианты: (а) буфер выключен, всё набирать
  руками; (б) буфер в обе стороны — копирование секретов внутри ВМ выносит их к хосту и в рабочую ВМ; (в) односторонний
  через `.vmx` (`copy.disable = TRUE`, `paste.disable = FALSE`) — проверен владельцем 06–07.11, в VMware Workstation не
  работает: `copy.disable` гасит буфер в обе стороны, а галочка Guest Isolation «Enable copy and paste» на работающей ВМ
  недоступна; (г) файл с командами и токеном через `sa-inbox` — отвергнут: пишется из рабочей ВМ, а отдельный файл
  обходит просмотр `review.sh`; (д) буфер VMware выключен, команды §3 владелец копирует внутри ops-ВМ из проверенного
  клона (`~/src/sosninaalbums-cloud/deploy/README.md`; буфер гостевой системы работает и при выключенном буфере VMware),
  токен CLO — одна загрузка ВМ с включённым буфером до появления в ВМ любых секретов: ВМ выкл → галочка вкл → под
  `sa-ops` `install -d -m 700 ~/sa-new && (umask 077; cat > ~/sa-new/clo_token)`, токен выпускается в панели и вставляется,
  буфер хоста затереть → ВМ выкл → галочка выкл → вкл, проверить, что вставка с хоста не работает; в §3 на вопрос
  `clo_token:` токен копируется внутри ВМ из `cat ~/sa-new/clo_token` (во второй вкладке), затем `shred -u ~/sa-new/clo_token`.
  Короткий токен (до ~40 знаков) можно просто набрать.
  **Выбор:** (д). Почему: наружу из ВМ ничего не уходит никогда; пока буфер включён, в ВМ нет секретов, кроме токена,
  который и так на машине владельца; команды берутся из проверенного клона. Защита токена в момент выпуска: окно
  браузера без расширений (инкогнито), без запущенных задач агентов, после вставки затереть буфер хоста (скопировать любое
  слово) и журнал Win+V, при сомнении отозвать и выпустить новый.

## 03.11.2026 — лицензия сервиса AGPL-3.0 (решение владельца)

- **Вопрос.** Под какой лицензией публиковать репозиторий сервиса: Apache-2.0, GPLv3 или AGPL-3.0.
- **Варианты.** Apache-2.0 (было): допускает закрытый платный клон сервиса. GPLv3: у сетевого сервиса не
  срабатывает — копии не распространяются, это «лазейка SaaS». AGPL-3.0: §13 обязывает открыть правки тому, кто
  даёт к ним доступ по сети.
- **Выбор.** AGPL-3.0 (решение владельца). `LICENSE` заменён текстом AGPL-3.0 без правок.
- **Почему.** Сервис работает по сети, и только AGPL закрывает лазейку SaaS. Модуль контракта `api/albums` в
  программе остаётся Apache-2.0: он совместим с AGPL-3.0, AGPL может включать Apache-2.0 код.
- **Ссылка «Исходный код» в листалке (§13).** Константа на публичный репозиторий
  `https://github.com/IliaSA101/sosninaalbums-cloud` в шаблонах страниц. Форк, меняющий код, сам меняет ссылку —
  это его обязанность по §13. Настройкой не делаем, чтобы не плодить конфиг.
- **Снимки `ci/*`.** Уже выгруженные до 03.11.2026 остаются под Apache-2.0.
