# 004. Выпуск образа albums-svc в GHCR

Статус: draft, редакция 3 — после второго круга аудита и второго мнения (07.11.2026).

Техрешение — [design.md](004-release-image/design.md); факты и отвергнутое — [research.md](004-release-image/research.md);
развилки — [decisions.md](decisions.md), «спека 004». Опора — 002-17 (GHCR, CI по метке, аттестация, дайджест в
приватном inventory, серверу ключи реестра не нужны). API `/v1` не меняется (контракт — в программе, 0.32/146).

## Зачем

Сервер берёт образ строго по дайджесту из inventory, а выпускать образ некому: CI кладёт его только в одноразовый
реестр стенда. Без выпуска нет первой раскатки.

## Посылка

На GitHub границы нет: агент рабочей ВМ ходит учётной записью владельца, прогон Actions сам просит права, а
переменные, секреты и раннеры репозитория меняются без коммита. Наборы правил и проверки в CI защищают от
`GITHUB_TOKEN` и ошибки. Граница одна — ops-ВМ: просмотренный коммит, проверенные кодом инварианты его workflow и
криптографическая привязка образа к нему.

## Поведение (сценарии)

1. **Выпуск.** «Да» владельца на `main` с лёгкой меткой `vX.Y.Z` (это и «да» на публикацию) → рабочая ВМ сверяет
   дерево `main` с зелёным `ci/*` → push → `release.yml`: `release-gate` ‖ `checks` (`check`, `build-image`,
   `stand-full`) → `release-publish` → `release-attest`. `D` — только вывод `build-image`; стенд проверяет тот же
   архив и может лишь сказать «нет»; `release-attest` до подписи сверяет через API, что все задания прогона шли
   на раннерах GitHub.
2. **Доставка.** Во входящие ops-ВМ — bundle с `main` и ровно два файла улик (аттестация, манифест). `review.sh
   main` — diff → «yes» → checkout коммита выпуска.
3. **Проверка, без сети.** `provision.sh image-verify vX.Y.Z`: (а) инварианты workflow в `HEAD` — `uses:` только из
   набора, сверенного с исходными репозиториями в окне Б, раннеры, контейнеры, переменные, секреты; (б) `gh
   attestation verify` по улике и корню Sigstore из inventory, `--source-digest` = `HEAD`; решение — по JSON
   каждого результата. `D` — из субъекта, в inventory его пишет сам код.
4. **Раскатка.** `configure`: проба слоёв GHCR до изменений, роль; после успеха — учёт раскатанной версии.
5. **Краевые.**
   - Метка не `vX.Y.Z`, не на `main`, не push → `release.yml` не стартует или `release-gate` отказывает.
   - Архив, стенд или тег GHCR расходятся с `D` → провал. Тег прочитан и указывает на чужой `D` → отказ, повтор —
     новой версией; ошибка чтения тега (в том числе `denied` до создания пакета) метку не сжигает: запись и
     обязательная сверка «тег → `D`».
   - Задание прогона на чужом раннере → `release-attest` не подписывает.
   - Улика, инвариант или пин не сходятся; корень без строки public good → код 3, inventory не тронут; подсказка
     про окно Б, если дело в корне или наборе действий.
   - Версия ниже **раскатанной** → отказ без `--allow-downgrade`; упавший `configure` новой версии откат к
     раскатанной не блокирует.
   - `configure` при коммите проверенного образа ≠ `HEAD` → код 3.
   - Пакет ещё приватный → проба отказывает; публичность — отдельное «да» до `configure`.
   - GHCR режется из ЦОД (как ECR, ВР-16) → проба падает по пределу времени до изменений.

## Требования

- `release.yml`: только `push` меток `v[0-9]+.[0-9]+.[0-9]+`; `permissions: {}`; без отмены прогона. Общее —
  `checks.yml` (`workflow_call`), его зовёт и `ci.yml`.
- Права: `contents: read` у проверок; `packages: write` — только `release-publish`; `id-token`,
  `attestations: write`, `actions: read` — только `release-attest` (без checkout и скачиваний). Кэшей нет.
- В workflow: `${{ }}` не в `run:`; `runs-on` — только `ubuntu-24.04`; нет `container:`, `services:`, `vars.`,
  `secrets: inherit`; `secrets.` — только `GITHUB_TOKEN` (и имя запасного токена); `environment:` — только у
  `release-publish` на запасном пути. Проверяет один скрипт — в CI и в `image-verify`.
- Действия: `uses:` по SHA из `deploy/release/actions.lock` (владельцы — только `actions`); lock сверяется в окне Б
  `git ls-remote` с метками исходного репозитория (импостор-коммит из форка не пройдёт), сверенный — в inventory.
- Артефакт образа — один файл в `runner.temp`; `publish.sh` — из sparse-checkout в подкаталог после скачивания.
- Образ `ghcr.io/iliasa101/albums-svc`, тег только `vX.Y.Z`; метки OCI; состав сверяется с эталоном.
- Метки `v*` лёгкие, не двигаются и не удаляются (это и версии Go-модуля в `sum.golang.org`).
- ops-ВМ раскатывает только коммиты `main`; полный diff и проверка невидимых символов `review.sh` — ещё и `.github/`,
  `go.mod`, `go.sum`.
- `gh` в ops-ВМ: адрес выпуска `cli/cli` и минимальная версия — константы кода; sha256 архива — в коде и сверен с
  выпуском в окне Б; запуск по ID образа, `--network=none`. Корень — `gh attestation trusted-root` в окне Б, в
  inventory, отдельным томом; из входящих — только два имени.
- До первой метки: токен рабочей ВМ — fine-grained без Administration (иначе агент регистрирует раннеры, правит
  переменные, снимает правила). Запасной токен публикации — design §9.

## Что доказывает аттестация

Доказывает: задание подписи шло на раннере GitHub, файл `release.yml` коммита `HEAD` по push метки `vX.Y.Z`
объявил субъект `D` (Fulcio, Rekor). Сверх неё: что `D` собран из `HEAD` на раннере GitHub без вмешательства, держат
проверенные инварианты workflow, пины действий, изоляция `build-image` и сверка раннеров через API. Не доказывает,
что кто-то прочёл код сервиса — `cmd`, `internal`, `web` (вместе с листалкой) и зависимости (`go.sum` — только
хэши) видны в `review.sh` лишь как `--stat` (остаток ниже).

## Модель угроз (новое)

| Угроза | Мера |
|---|---|
| Непросмотренный коммит в образе | `--source-digest` = `HEAD`; раскатка только коммита выпуска |
| Подменённое действие (SHA из форка) | lock + `ls-remote` в окне Б; `image-verify` — пины только из сверенного набора |
| Сборка вне просмотренного кода (свой раннер, контейнер, переменные, секреты) | инварианты кодом в `image-verify`; API раннеров в `release-attest`; токен без Administration |
| Стенд подменяет образ или `D` | `D` — вывод `build-image`; `publish`/`attest` сверяют архив |
| Внедрение через имя метки, отравление артефакта | `env:` + регулярное выражение; `runner.temp`, один файл |
| Перевес тегов GHCR из `ci/*` | сервер и ops-ВМ берут только `D`; третьим лицам — «только по дайджесту с проверкой» |
| Откат на старый подлинный выпуск | порог — раскатанная версия; ниже — только флаг |
| Подложенный корень или старый `gh` | корень из inventory, отдельно от улик; минимум версии и адрес — константы |
| Запасной токен | без `repo`, на день; агент в окне может его прочесть — секрет удаляется сразу |
| GHCR недоступен из ЦОД | проба до изменений; план Б — отдельная спека |

**Принятые остатки.** Код сервиса и зависимости читают только ревью и аудит пачек; закладку сдерживает контейнер
(`Network=none`, корень только для чтения, без capabilities) — наружу лишь через ответы HTTP. Любой прогон `ci/*`
может перевесить любой тег GHCR — третьи лица, берущие по тегу, гарантий не имеют. Числовой id владельца не
проверяется: пересоздание ловит id репозитория, передачу — имена в `-R` и `--signer-workflow`.

## Критерии приёмки

Полные списки случаев — design §12. На `ci/*` и в стенде: `workflow_guard_bypass`, `workflow_static`, `release_gate_cases`,
`image_composition`, `stand_archive_mode`, `release_publish_cases`, `runner_check_cases`, `actions_pins_cases`,
`image_verify_cases`, `review_ctl_cases`, `configure_image_cases`, `ghcr_probe_cases`. На первом выпуске: цепочка `D`
одна; `image-verify` — код 0; анонимный `podman pull …@D`; своя аттестация — фикстура с боевыми константами. На
пробной аренде: проба и `pull` целиком, время записано, предел — по замеру.

## Не входит

- Воспроизводимость байт в байт, SBOM, cosign с ключом, несколько архитектур, Release.
- `podman auto-update` по тегу (обход ops-ВМ); план Б доставки — отдельная спека.

## Задачи по зонам

| № | Зона | Что | Готово, когда |
|---|---|---|---|
| И6a | инфраструктура | `checks.yml`, `ci.yml`, `release.yml`; `build-image`, эталон; режим архива; `gate.sh`, `publish.sh`, `workflow_guard.py`, `actions.lock`; проверка раннеров; сверка дерева | критерии CI |
| И6b | инфраструктура (ops) | `image-verify`; `gh`, корень и пины в окне Б; `verified-image`/`deployed-image`, улики по версиям; `configure`; `review.sh`; inventory-пример; README | `image_verify_cases`, `actions_pins_cases`, `review_ctl_cases`, `configure_image_cases` |
| И6c | инфраструктура | проба GHCR (`ops/ghcr_probe.py`, первое действие `configure`), предел `pull` (`albums_svc_pull_timeout_sec`) | `ghcr_probe_cases`; предел — по аренде (до замера 600 с) |

Порядок: И6a ‖ И6b → И6c → аудит (CI, ops-ВМ) → первый выпуск (design §9). Объём: И6a — 1–1,5 сессии и 2–3 круга
`ci/*`; И6b — 1,5 сессии; И6c — полсессии.

**Необратимое:** публичность пакета; метка и коммит `main`; записи Rekor; личность подписанта (аккаунт,
репозиторий, `release.yml`, id) — переименование меняет константы и имя образа.
